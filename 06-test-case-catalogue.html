7. Test data strategy note

Static / environment-seeded (read-only — tests must never mutate these):

  • Admin / admin123 account — the only pre-existing data any test may depend on. Injected via OHRM_USERNAME / OHRM_PASSWORD env vars (.env locally, CI secrets), never hard-coded in specs.
  • Reference/config data shipped with the demo: leave types (e.g., CAN - Vacation), user roles (Admin, ESS), statuses (Enabled/Disabled). Treated as stable vocabulary; if a demo upgrade renames them, it's a one-file fixture fix.

Generated per run (owned by the test that creates it):

  • Employees: Auto / User-<ts> with employee id <ts5> from uniqueEmployee() — <ts> is a per-run epoch-millis stamp, so parallel workers and other visitors to the shared tenant cannot collide.
  • System users: autouser<ts>, passwords Str0ng!Pass<ts> (policy-compliant by construction).
  • Leave entitlements and requests: entitlement is seeded at the start of the Leave suite by the suite's own setup (Assign Entitlement flow), never assumed to pre-exist — the demo resets wipe it.

Independence rules (how tests stay isolated from each other):

  1. Create-your-own: a test (or its beforeEach/suite setup) creates every record it asserts on. No test searches for another test's data or for hand-seeded demo employees.
  2. Assert on identity, not totals: assertions target the uniquely-named record ("1 row for User-<ts>"), never global counts, which other tenant users constantly change.
  3. Chain only inside a documented dependency: where a case intentionally builds on another (TC-ADM-008 on 005, TC-LEA-006/007 on 002), the dependency is stated in Preconditions and both run within one serial describe-block; across blocks, order independence is mandatory.
  4. Best-effort cleanup: teardown deletes created employees/users/leave; cleanup failure logs a warning but never fails the test, because the shared demo may have already reset underneath us (Risk R1, TP §7).
  5. One auth, many tests: authentication state is established once per worker (storageState / cy.session()); only Login-module cases exercise the login UI, removing the most flake-prone step from 44 of the 55 cases.
