Artifact 11 — Executive Summary: OrangeHRM Quality Assessment

For: Client stakeholders (non-technical) | From: QA Lead | Date: 20 July 2026 | One page

What we did

Over a six-week engagement we tested the five most business-critical areas of the OrangeHRM system: signing in, managing user accounts, maintaining employee records, requesting leave, and the home dashboard. Every important behaviour was written down as a formal test (55 in total), and each test was automated twice, using two independent industry-standard tools, so results could be cross-checked. The full set of checks now runs automatically every night and on every code change — meaning future updates to the system will be verified within minutes, not days.

Overall quality assessment

The core of the system is in good shape. Signing in, employee record-keeping, and user administration passed every test, repeatedly, including deliberate attempts to break them with bad input. Of 53 checks completed, 52 passed — a 98% pass rate, with both tool sets in full agreement.

We found four genuine issues. Two matter for a launch decision:

  1. Leave requests can be saved with impossible dates. If a user types dates by hand (rather than clicking the calendar), the system accepts a leave request that ends before it starts. These invalid records flow into approvals and leave balances. The data damage is silent, which is exactly the kind of issue that gets expensive if it reaches production. A fix is straightforward and well understood.
  2. The platform occasionally fails to load at all. Roughly one page-load in a dozen, during busy periods, the login page returns a server error for a few seconds. We believe this is the shared demo server rather than the application itself — but that must be confirmed on production-grade infrastructure before launch, because when it happens, nobody can use the system.

The other two issues are minor: a screen that shows an employee's old name until refreshed after a rename, and a technical error message in the browser's background log that users never see.

Key risks

  • Data integrity in Leave (issue 1) is the main business risk — it corrupts records quietly.
  • Platform stability (issue 2) is unquantified until tested on real infrastructure.
  • Two leave-related checks could not be completed because the shared demo environment erases its data periodically; they are scheduled for a re-run. This is a limitation of the demo environment, not of the system's design.

Recommendation: GO, with two conditions

We recommend proceeding, conditional on:

  1. Fixing the leave date-entry issue and re-running the affected checks (small, well-scoped fix);
  2. A short stability check of the login service on production-representative infrastructure.

Sign-in, employee records, user administration, and the dashboard are ready today. Once the two conditions are met, the automated test suite — which now guards all five areas on every future change — gives strong ongoing protection against regressions.
