Artifact 5 — Low-Level Design (LLD): Login & PIM Modules

Project: OrangeHRM Demo Automation | Author: QA Lead | Version: 1.0 Scope of this LLD: Login module, PIM (employee records) module. Signatures shown in Playwright-flavoured JavaScript; the Cypress implementation keeps identical class/method names with tool-idiomatic bodies (sync command chains, no async).

Interfaces only — no implementation bodies. This document is the contract the build phase implements.

1. Login module

1.1 Page object class structure

BasePage
 └── LoginPage
DashboardPage        (assertion target after successful login — owned by Dashboard LLD,
                      referenced here only for the post-login handoff)

LoginPage is deliberately flat — one screen, one class. The forgot-password screen is small enough to live as a section of LoginPage rather than its own class; if it grows, extract ForgotPasswordPage later.

1.2 LoginPage — method signatures

class LoginPage extends BasePage {
  // --- navigation ---
  async goto()                              // open /auth/login, wait for form visible

  // --- atomic actions ---
  async enterUsername(username)             // fill username field
  async enterPassword(password)             // fill password field
  async submit()                            // click Login button

  // --- composite action (the one specs normally use) ---
  async loginAs({ username, password })     // goto + fill both + submit

  // --- state readers (return values; specs assert) ---
  async getErrorMessage()                   // → string: "Invalid credentials" banner text, or null
  async getFieldValidationMessages()        // → string[]: per-field "Required" messages
  async isLoginFormVisible()                // → boolean

  // --- secondary flows ---
  async clickForgotPassword()               // navigate to reset screen
  async getForgotPasswordHeading()          // → string, for navigation assertion
}

Design rules visible in the signatures:

  • Readers return, specs assert. getErrorMessage() returns a string; the spec does expect(msg).toBe('Invalid credentials'). The page object never imports expect for business outcomes (visibility waits inside actions are allowed — they're synchronisation, not verdicts).
  • Composite + atomic both exposed. loginAs() serves 90% of specs; atomic methods exist for the negative matrix (e.g., submit with only username filled).

2. PIM module

2.1 Page object class structure

BasePage
 └── PIMListPage          — employee list: search, grid, delete
 └── AddEmployeePage      — the Add Employee form (create flow)
 └── EmployeeDetailsPage  — Personal Details tab of an existing employee (edit flow)

Three classes because PIM has three genuinely distinct screens with distinct responsibilities; collapsing them into one "PIMPage" was rejected — it would exceed ~25 methods and mix search-grid logic with form logic.

2.2 Method signatures

class PIMListPage extends BasePage {
  async goto()                                  // navigate via left menu → PIM, wait for grid

  // --- search ---
  async searchByName(employeeName)              // type-ahead field + Search
  async searchById(employeeId)
  async resetSearch()

  // --- grid readers ---
  async getRecordCountText()                    // → string, e.g. "(1) Record Found"
  async getRowByName(employeeName)              // → row handle/locator or null
  async isEmployeeListed(employeeName)          // → boolean

  // --- row actions ---
  async openEmployee(employeeName)              // click row → EmployeeDetailsPage context
  async deleteEmployee(employeeName)            // trash icon + confirm dialog
  async getToastMessage()                       // → string ("Successfully Deleted", …)

  // --- entry point to create flow ---
  async clickAddEmployee()                      // + Add → AddEmployeePage context
}

class AddEmployeePage extends BasePage {
  async fillName({ firstName, middleName, lastName })
  async setEmployeeId(employeeId)               // overwrite auto-generated ID
  async toggleCreateLoginDetails(enabled)
  async fillLoginDetails({ username, password, confirmPassword, status })
  async save()                                  // submit; wait for navigation/toast
  async getValidationMessages()                 // → string[] (e.g. passwords mismatch)
}

class EmployeeDetailsPage extends BasePage {
  async isLoaded()                              // → boolean: Personal Details header + name
  async getHeaderName()                         // → string (name shown in the header)
  async updatePersonalDetails({ ...fields })    // nickname, other id, driver's licence…
  async save()
  async getToastMessage()                       // → string ("Successfully Updated")
  async getFieldValue(fieldLabel)               // → string, generic reader for asserts
}

Save buttons getByRole('button', { name: 'Save' }) scoped to the active form 1 (scoped) Details page has multiple Save buttons (one per card) — scope to the card under edit

Key rules:

  • Every PIM test owns its data. uniqueEmployee() stamps a per-run timestamp so parallel workers and other demo-site visitors can't collide (Risks R1/R2). No test searches for a hard-coded "Paul Collings"-style seeded employee.
  • Create-then-verify-then-delete is the standard shape; delete failures in teardown are logged but don't fail the test (shared env may have already reset).
  • Objects, not positional args: fillName({ firstName, lastName }) keeps call sites readable and lets the invalid-data tests omit fields naturally.
  • Auth is pre-established (storageState / cy.session() per HLD §6): PIM specs start on an authenticated session and call PIMListPage.goto() directly — no UI login per test.

3. Shared LLD conventions (both modules)

  1. Constructor contract: every page object takes the driver handle (page in Playwright; nothing in Cypress — cy is ambient) and defines all locators in the constructor or as getters — never inline inside methods.
  2. Waiting: actions end when the UI is ready for the next step (e.g., save() resolves after the toast or navigation), so specs never insert waits.
  3. Return-type discipline: action methods return void/this; reader methods return primitives or plain objects; nothing returns raw locators to specs.
  4. Naming: goto* navigation, get* readers, is* booleans, verbs for actions — identical names across the Cypress and Playwright implementations to keep the parity review mechanical.
